# Browser session security assessment — 18 October 2026

**Repository remediation verified locally; public launch remains blocked.** This supplements the [application assessment and its 15-area checklist](security-assessment-2026-10-17.md), [outbound containment](outbound-request-containment-2026-10-17.md) and [administrator replay/inactivity controls](admin-session-security-2026-10-18.md). It is not independent penetration testing or an ASVS certification.

## Scope and architecture

Baseline `e4818909cff9f8c54d00b8d9c3388a342eb5fcae`, branch `codex/public-launch-rc1`. Browsers authenticate to Next.js session handlers, receive encrypted HttpOnly cookies and use same-origin proxies. Those proxies forward server-held credentials to Express; its fresh database authorization and operator inactivity/absolute limits remain authoritative. NextAuth's verified Google identity can establish a merchant session through a separate bridge. Middleware's cryptographic cookie check is not a live backend revocation check.

The broader assessment covers Express/Prisma/PostgreSQL, Redis limits and queues, S3 media/erasure, SDK/storefront tokens, webhooks/catalog fetching, private Python inference and deployment/CI controls. This follow-up changes browser sessions and their operator journey. Concurrent lower-body work is excluded from this patch. No external infrastructure, real identities or customer data were attacked.

## Findings, priority and affected files

| Finding | Severity / demonstrated behavior | Remediation and affected files |
|---|---|---|
| WEB-01: custom session cookies lacked browser-enforced host prefixes | Medium, defense in depth. Existing encryption, HttpOnly, SameSite and production Secure flags already protected their values. Missing prefixes weakened resistance to cookie injection by a compromised sibling host; no authentication forgery was demonstrated. | `apps/web/app/lib/session-cookie.ts` centralizes policy. Admin/dashboard session modules use production `__Host-drapixai_admin_session` / `__Host-drapixai_dashboard_session`. Password login, OAuth bridge, logout and proxy handlers consistently apply Secure, HttpOnly, Strict, root Path and no Domain. Production never falls back to legacy names. |
| WEB-02: stale browser state after backend session rejection | Low, session-lifecycle/usability weakness. API authorization already rejected expired/revoked credentials; later admin actions did not consistently navigate back to login, and cookies remained until local expiry/logout. This was not an API authorization bypass. | Admin proxy clears both cookie names on 401/403; merchant proxy clears on 401 and preserves ordinary permission-denied 403 sessions. `apps/web/app/lib/admin-fetch.ts`, used by `apps/web/app/admin/page.tsx`, redirects once, stops subsequent requests and discards late successful responses after expiry. Requests already in flight are not retroactively cancelled or unauthorized by this UI helper. |
| WEB-03: administrator password normalization changed credentials | Low, compatibility defect. The session handler stripped significant leading/trailing whitespace, denying otherwise valid exact passwords in the fixture. | `apps/web/app/api/admin/session/route.ts` preserves password bytes as supplied in the JSON string, normalizes email only, and rejects malformed email/password types before contacting the backend. Password hashing and the MFA challenge are unchanged. |

The encrypted token format now authenticates the cookie name as AES-GCM additional data and rejects extra token segments. Old ciphertext cannot be copied into the new cookie name. This is defense in depth and deliberately invalidates old browser cookies, including development cookies. It does not cryptographically bind tokens to an individual hostname or replace secret separation/key rotation.

The HTTPS harness uses ephemeral loopback listeners, synthetic passwords/keys/SSO tokens, and a generated one-day self-signed test certificate. It blocks browser requests outside its two loopback-mapped origins, ignores that test certificate only in its fresh browser context, closes its own servers/browser and restores Next's generated source configuration. It requires existing Playwright/Chrome and test-only Python `cryptography`; it does not install them or change trust stores. Run with Node 22 and `DRAPIXAI_BROWSER_MODULES` pointing to the existing directory containing Playwright; optionally set `DRAPIXAI_FIXTURE_PYTHON`. The isolated build is `.next-browser-session-audit`.

Reports/logs and synthetic TLS files remain ignored under `runtime/launch-evidence/browser-sessions-2026-10-18/`. Browser evidence records source hashes and explicitly marks the checkout dirty; it is local candidate evidence. It is **not** a clean-release staging attestation. The Google provider itself, real MFA, actual backend expiry/revocation, real merchant installation and trusted public TLS are outside this browser fixture. Backend replay/inactivity has separate real disposable-PostgreSQL coverage in the administrator report.

## Rollout and unresolved risks

1. Deploy coordinated web replicas with the new cookie format. **Existing admin and merchant browser sessions require login again.** Development names remain unprefixed for HTTP, but the authenticated token-format change also requires one development relogin. Never add a legacy authentication fallback. OAuth identities may use the bridge again; a fresh operator password/TOTP challenge is still required for admin access.
2. Login/logout/rejection retire the old root, host-only cookie. They do not claim to delete every historical parent-domain/path cookie. Such legacy names are ignored by production authentication. Keep secrets distinct and verify the actual domain/CDN/proxy configuration.
3. The preceding additive `20261017120000_admin_mfa_replay` migration must precede API replicas requiring that column; this browser follow-up adds no migration. Old API authentication replicas still permitting TOTP reuse/idle revival must be drained. Test real expiry, revocation, recovery/offboarding, MFA clock/rotation policy and cookie migration in staging.
4. **Blocking:** Accelerate `1.11.0 / PYSEC-2026-3804` remains unresolved in the last verified AI CI job. Isolated candidate checks do not authorize promotion. Node's embedded OpenSSL review also remains open despite successful distro/container scans.
5. **Blocking:** live isolated staging is unprovisioned; actual HTTPS/mTLS, Redis ACL/network isolation, trusted queue writers, encryption/retention across logs/backups/versions, edge slow-request limits, key rotation, restore and incident/deletion drills lack operational evidence. Individual operator MFA enrollment/recovery, bcrypt's 72-byte boundary and Google account-link lifecycle still need review.
6. **Blocking:** no independent penetration-test report/remediation retest, controlled real merchant pilot, commercial CatVTON rights clearance, qualified legal/founder approval or delivered-workstation/GPU acceptance exists in the reviewed evidence. Standard SDK/direct parity and four simultaneous independently scored >=0.95, warning-free, visually reviewed outputs with isolation/latency/VRAM/soak evidence remain required.
