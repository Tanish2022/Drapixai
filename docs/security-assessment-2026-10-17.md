# DrapixAI application security assessment — 17 October 2026

**Disposition: application weaknesses remediated and locally verified; public launch remains blocked.** This is a repository assessment with bounded local tests, not an independent penetration test, an ASVS certification, or proof that production is secure.

## Scope, method and architecture

Baseline: `1f033326eec2efe74c9d0d8a7ec7bf9140f89e96`, branch `codex/public-launch-rc1`. Reviewed the Next.js website and server-side authentication/proxies, Express API and Prisma access paths, JavaScript/React SDK rendering and token use, private Python inference boundary, storage/retention controls, deployment configuration, dependency/security CI and secret-scanning policy. Concurrent lower-body development was present in the worktree and is outside this change set.

The browser reaches Next.js/NextAuth and same-origin session/proxy handlers. The Express API uses PostgreSQL through Prisma, Redis for distributed limits/capacity, S3-compatible object storage, Stripe-hosted billing and optional Shopify catalog integration. SDK/storefront requests use scoped credentials and server-owned product/media access. The private FastAPI inference service is reached through a service-authenticated, production mTLS boundary; GPU workers execute the existing model pipeline. Webhooks/catalog discovery are outbound network boundaries. Administrator APIs intentionally have cross-tenant powers and therefore require a separate operator authorization boundary.

Method: architecture/source inspection; query, render, credential and request-boundary searches; TypeScript checking; real route/module execution with synthetic identities and database/network adapters; existing regression suites; a production web build and loopback-only CSP checks; active secret-scanner policy validation and history scanning. No external target was attacked. No customer database, merchant account or real storage object was used for destructive testing. The storage-erasure suite uses its own loopback S3 XML fixture and fake database. No GPU inference was run. No dedicated Semgrep/Bandit scan or independent DAST engagement was performed.

Framework versions were checked against their primary publications: [OWASP Top 10:2025](https://top10.owasp.org/2025/), [OWASP API Security Top 10:2023](https://owasp.org/API-Security/editions/2023/en/0x11-t10/), and [ASVS 5.0.0](https://owasp.org/www-project-application-security-verification-standard/). The mappings below identify relevant control families; they are not a claim that every ASVS requirement or Level 2 has been verified.

## Findings and remediation

Severity is qualitative and reflects the demonstrated access prerequisite and likely business impact. Local tests establish code behavior, not successful exploitation of a deployed service. All nine items below are fixed in source; deployment has not been verified.

| ID | Severity | Verified weakness and impact | Affected implementation and remediation | Verification |
|---|---|---|---|---|
| SEC-01 | High | The Google synchronization path could issue a dashboard key for a privileged account without the local password/TOTP challenge. The administrator API accepted that key. An authenticated Google identity matching the configured operator could bypass the additional local MFA requirement; this was not unauthenticated administrator takeover. | `apps/api/src/routes/auth.ts`, `apps/api/src/lib/admin-mfa.ts`, `apps/api/src/routes/admin.ts`: reject privileged Google synchronization before writes/key issuance; password/TOTP login alone issues `admin:mfa` dashboard keys, with an eight-hour absolute expiry. Admin APIs require that assurance in addition to fresh database role and configured operator identity. | Real route fixtures deny privileged OAuth and old/non-MFA keys, require TOTP, check scope/expiry and accept the assured operator key. Merchant OAuth remains usable. |
| SEC-02 | Medium | Public API result lookup checked merchant ownership but omitted the product restriction embedded in a scoped token. Completed idempotency replay had the same gap. A valid token could read another product's result within its own merchant account. Cross-tenant disclosure was not demonstrated. | `apps/api/src/routes/v1.ts`: enforce the existing `isStorefrontProductAllowed` control on result lookup and replay before returning any result/rejection metadata. Disallowed lookup returns 404; disallowed completed replay follows the existing unavailable-result 409 path. | Four positive/negative route cases exercise lookup and replay with allowed/disallowed products and ensure the disallowed result identifier is absent. |
| SEC-03 | Medium | The web proxy read the whole request with `arrayBuffer()` before enforcing the limit. An undeclared/chunked large upload could exhaust process memory before rejection. No crash/load attack was run. | `apps/web/app/lib/request-guard.ts`: count streamed bytes, cancel immediately above the configured cap, release the reader and assemble only accepted bodies. Existing declared-length and method checks remain. | Synthetic stream rejects on the second chunk without a bulk read; exact-boundary binary payload is preserved. An upstream server may still buffer before this handler: staging verification is required. |
| SEC-04 | Medium | Some rate-limit keys used literal request paths, allowing an authenticated caller to rotate object identifiers into different buckets. This weakened abuse/resource controls. | `apps/api/src/lib/rate-limit.ts`, `apps/api/src/routes/v1.ts`: use matched route templates; middleware before a route match shares a mount-wide cap. Apply the same stable key to public API key/tenant limits. Numeric thresholds are unchanged. | Two different result IDs share a bucket and the second request receives 429 at a one-request fixture limit; unknown paths under the same mount share a key. Distributed multi-replica behavior still needs staging evidence. |
| SEC-05 | Medium, network-dependent | Partial outbound address checks accepted shared/benchmark IPv4 space, noncanonical mapped private IPv6 and parts of IPv6 link-local space. A configured merchant destination resolving there could reach internal services if the deployment routes them. No internal service access or data exfiltration was attempted. | New `apps/api/src/lib/network-address.ts`; `apps/api/src/lib/remote-fetch.ts`, `apps/api/src/routes/v1.ts`: one URL/address policy for webhook registration and outbound fetching, reject local/special/translation/tunnel addresses, inspect every DNS answer, retain pinned connection lookup and reject redirects. Explicit address family preserves pinning under Node 22. | Four formerly accepted DNS answers are rejected before transport creation. Mixed public/private answers fail closed. Public IPv4/native IPv6 and mapped public IPv4 positives pass; a synthetic successful request verifies its pinned address/family and response. |
| SEC-06 | Low, identity hardening | The application callback trusted the Google email without explicitly requiring the verified-email claim and matching it to the callback user. A false claim was accepted by the local callback fixture; a real Google-provider exploitation path was not demonstrated. | `apps/web/app/api/auth/[...nextauth]/route.ts`: require `email_verified === true` and normalized profile/user email equality before backend synchronization. Existing NextAuth provider validation remains in place. | False verified-email claim is denied before any fetch; a matching verified merchant profile succeeds. |
| SEC-07 | Low, defense in depth | JWT verification checked signature/algorithm/issuer/audience, but accepted correctly signed public tokens with absent expiry, excessive lifetime or a future issuance timestamp. This requires a trusted issuer/signing key; it is not a demonstrated signature bypass. | `apps/api/src/lib/api-key-auth.ts`: require integer `iat`/`exp`, increasing bounded lifetime, issuance no more than 30 seconds ahead and library-enforced maximum age. Public API/preview cap 900 seconds; storefront cap 300 seconds. Existing parent-key revocation and bounded key overlap remain. | Missing expiry, overlong, future-issued, wrong audience/issuer/algorithm and expired tokens fail. Normal issued and overlapping-key tokens pass; parent-key revocation overrides an otherwise valid token. |
| SEC-08 | Low, defense in depth | A present malformed or `null` Origin fell back to Referer validation. This allowed contradictory origin evidence in synthetic requests; a browser-exploitable CSRF attack was not established. | `apps/web/app/lib/request-guard.ts`: a present Origin must parse and match; Referer fallback is available only when Origin is absent. | Null/malformed/foreign Origin with a same-origin Referer is denied; same-origin Origin and absent-Origin/same-origin Referer remain accepted; production requests with neither fail closed. |
| SEC-09 | Medium | The outbound GET response's error listener was installed after its declared-size check. An oversized response was destroyed with an error before any response error listener existed, leaving an unhandled-error path. A synthetic EventEmitter reproduction failed with `UNHANDLED_RESPONSE_ERROR`; no deployed process was crashed. | `apps/api/src/lib/remote-fetch.ts`: install the response error handler before status/header/size processing, retaining rejection through the request promise. | Oversized declared response now rejects as `REMOTE_RESPONSE_TOO_LARGE` through the installed listener. The added case failed before the fix and passes afterwards. |

SEC-01 maps to Top 10 A01/A07, API2/API5 and ASVS authentication/session/authorization controls. SEC-02 maps to A01, API1/API3 and object authorization. SEC-03/04 map to A06/API4/API6 and resource/abuse controls. SEC-05 maps to A01/API7/API10 and outbound network validation. SEC-06/07 map to A07/API2 and identity/token verification. SEC-08 maps to A01 and browser request integrity. SEC-09 maps to A10/API4/API10 and error/resource handling.

The [Google OpenID Connect documentation](https://developers.google.com/identity/openid-connect/openid-connect) describes the verified-email claim and limits of email authority; enterprise account-linking/lifecycle policies still require review. The outbound policy is deliberately conservative relative to [IANA IPv4](https://www.iana.org/assignments/iana-ipv4-special-registry/iana-ipv4-special-registry.xhtml) and [IPv6 special-purpose registries](https://www.iana.org/assignments/iana-ipv6-special-registry/iana-ipv6-special-registry.xhtml): globally reachable special protocols/tunnels are not required merchant destinations. Do not relax it to permit private endpoints without a separate network-isolated integration design.

## Rollout and preservation

Deploy API and web fixes coherently across all replicas. Existing operator keys without `admin:mfa` intentionally stop authorizing administrator routes: operators must perform a fresh password/TOTP login. Keys issued through that login expire after eight hours; a Google session cannot replace the local operator challenge. Check both allowed merchant flows and denied operator OAuth during staging smoke tests. Do not keep an old API replica accepting unassured keys. A rollback to the old implementation reintroduces the vulnerabilities.

No model weights, inference code, Standard CatVTON settings, worker capacity, quality thresholds or original 22 release-evidence decisions were changed by this security patch. The release profile `deploy/release/standard-catvton-rc1.env` remains protected; its baseline SHA-256 is `b732cd2b227a34a9bdfb65ff08cbacb3abd87846be589ba1a58e98199a012762`. This source-preservation check is not GPU quality proof. Concurrent lower-body work remains separate and was not included in this audit commit.
