Project Dossier

DrapixAI

DrapixAI is a fashion ecommerce AI try-on platform built for controlled storefront rollout. The current product is focused on upper-body virtual try-on, standard-quality generation, confirmed product mapping, garment caching, and launch-safe operations.

Primary market Fashion ecommerce brands and storefront teams
Current launch scope Upper-body garments only, standard quality only
Deployment target Edge web/API + RunPod A100 GPU AI runtime

1. Executive Summary

DrapixAI helps brands let shoppers preview clothing on themselves without needing a heavy storefront rebuild. The product is designed to be reliable before it is broad. That means the launch scope is intentionally narrow, the AI pipeline is guarded by validation rules, and brands are expected to confirm product-to-garment mappings before live shopper traffic uses the system.

Core positioning: AI virtual try-on for fashion ecommerce, starting with upper-body garments and a monitored rollout model.
Upper-body only Standard quality only Confirmed mapping flow Garment cache required A100-ready deployment

2. Product Overview

What the product does

  • Lets a brand upload isolated garment images.
  • Validates and preprocesses those garment images into reusable cached assets.
  • Syncs a product catalog and suggests garment-to-product matches.
  • Requires manual confirmation of the final mapping before storefront use.
  • Accepts a shopper photo plus a product identifier and returns a generated try-on image.
  • Returns operational metadata such as quality score, latency, warnings, engine, and cache state.

Launch-ready garment scope

The strongest current categories are shirts, t-shirts, polos, blouses, and clean tops. Short kurtis, hoodies, and sweatshirts are treated more carefully. Long kurtas, jackets, blazers, layered outerwear, and other broader full-body categories are outside the current public promise.

What DrapixAI is not promising yet

  • Full-body try-on is not part of the current live launch promise.
  • It should not be marketed as a universal solution for every garment class.
  • It should not be framed as a fully hands-off SaaS product yet.

3. Customer Workflow

  1. Create an account and receive an API key.
  2. Upload garment-only images for validation and cache generation.
  3. Discover or sync catalog products into the dashboard.
  4. Review suggested matches and confirm the correct garment-to-product pairings.
  5. Install the SDK or call the REST API with a shopper photo and confirmed product mapping.
  6. Receive a try-on image plus metadata for analytics and quality review.
Business benefit Better product-page engagement, stronger purchase confidence, and a more controlled rollout path for brands testing AI commerce.
Operational benefit Cached garments, domain controls, review workflows, readiness checks, and analytics reduce launch risk.

5. Pricing and Commercial Model

  • Free trial: 300 try-ons over 12 days.
  • Starter: entry paid plan for smaller brands.
  • Growth: higher-volume plan for growing stores.
  • Pro: shown as future-facing / coming soon.
  • Enterprise: custom commercial path through sales.

The commercial story is designed to be low-friction: brands try the workflow first, validate quality on their own garments, then move into paid volume only if the output and integration path are strong enough.

Commercial note: the repo indicates a small mismatch between some pricing language and backend quota configuration, so pricing and quota values should be checked before public billing is treated as final.

6. Technical Architecture

Web application

  • Framework: Next.js 16 with React 18
  • UI: Tailwind CSS and app-router pages
  • Auth session support via NextAuth

Backend API

  • Runtime: Node.js with Express and TypeScript
  • Database ORM: Prisma
  • Primary services: auth, SDK routes, analytics, admin, account, public endpoints
  • Email: Nodemailer-based SMTP integration
  • Scheduling: node-cron for time-based account lifecycle work

AI service

  • Runtime: Python FastAPI service
  • Core engine: CatVTON-based try-on pipeline
  • Upper-body validation and garment preprocessing
  • Garment cache and request metadata headers
  • Redis-backed queue and job lifecycle

8. AI Runtime Details

  • Preferred production environment: RunPod Ubuntu GPU stack
  • Recommended GPU: A100 PCIe 80GB
  • Base image: RunPod PyTorch 2.4.0, Python 3.11, CUDA 12.4.1
  • Preset environment: DRAPIXAI_GPU_PRESET=runpod-a100
  • Current launch quality mode: standard only
  • Warm latency target: roughly 10 to 12 seconds
  • Model preload enabled on the A100 path to reduce first-request cold start

AI safeguards already reflected in code

  • Rejects unsupported non-standard quality requests.
  • Restricts launch flow to upper-body try-on.
  • Requires internal API-to-AI service token for protected AI routes.
  • Attaches quality, timing, and garment-source metadata to responses.

9. Data Model

The core persisted entities in the database include:

  • User: account, company, plan, trial, store verification, sync metadata
  • ApiKey: active key lifecycle and domain whitelist
  • Usage / UsageDaily: monthly and daily quota accounting
  • Garment: uploaded garment record, cache key, status, thumbnails, source information
  • CatalogProduct: synced product catalog entries
  • GarmentMatch: suggested and confirmed garment-to-product links
  • TryOnResult: result image, quality score, warnings, timing, approvals
  • TryOnFeedback: human review and error labeling for realism issues
  • EmailLog: transactional email send tracking
  • VerificationCode: OTP and verification flow support

10. Security and Operational Controls

  • Helmet and CORS protection on the API.
  • JWT-based auth for account sessions.
  • Bcrypt hashing for passwords and API key storage.
  • Single-domain enforcement behavior for SDK/API keys.
  • Readiness checks across database, Redis, AI, and storage.
  • Admin review support for low quality, high latency, warning-heavy, or cache-failed cases.
  • Email event logging for OTP and workflow notifications.

12. Launch Readiness

What appears ready now: deployment documentation, production environment templates, API and web build expectations, launch-readiness assertions, RunPod bootstrap scripts, health checks, and smoke-test flow.
Main live blockers still called out in project docs: live RunPod A100 validation, real SMTP verification, optional Google OAuth verification, and one successful end-to-end public try-on on the Linux GPU stack.

Go-live conditions reflected in repo docs

  • A100 deployment must pass health and ready checks.
  • At least one real staging try-on must complete end to end.
  • Signup, login, dashboard, garment flow, and SDK flow must be verified.
  • Support inboxes should be live: support, sales, and privacy.

13. Practical Summary

DrapixAI is best understood as a controlled AI commerce system rather than just an image generator. The product combines garment validation, product mapping, AI generation, analytics, operational review, and launch guardrails into one workflow for fashion brands.

The project is technically mature enough to show serious launch preparation, but it still depends on final live validation of the GPU production path and email infrastructure before it should be treated as fully public-ready.
